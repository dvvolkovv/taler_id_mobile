# Group Mesh Voice Room — Design Spec

**Date:** 2026-05-13
**Status:** Draft, awaiting user review
**Authors:** brainstormed with Claude

## Goal

Build a voice room for 2-5 participants on the same Wi-Fi without any server for audio or signaling. Extension of Phase 3 mesh voice (1-on-1, libopus + Bonjour + UDP datagrams + Noise IK) to N peers in full-mesh topology.

## Motivation

- Long-term product vision: communication without servers, eventually without even shared Wi-Fi (Wi-Fi Direct / Multipeer in a later phase).
- LiveKit-based group call (Phase 1) has 7 unresolved polish defects gating PROD; rather than fixing them, redirect effort to the mesh-native path that aligns with the product direction.
- 1-on-1 mesh voice already works on the same Wi-Fi (v1.0.67 PROD); the infrastructure (libopus FFI, `MeshDatagramCipher`, Bonjour UDP, Noise IK, `MeshDiscoverySupervisor`, multi-userPk handling) is ready to host N peers with focused additions.

## Scope (v1)

**In scope:**

- Room creation: host picks 2-4 contacts from the address book.
- Invite delivery as mesh envelopes (Phase 2 messaging path), per-invitee.
- Native incoming UI: CallKit on iOS, full-screen notification on Android via the Phase 3d.3 background-mesh mechanism.
- Accept / Decline in a lobby; transition to Active when all accept (or 30 s timeout, with anyone who did not answer dropping out).
- Active phase: N(N-1)/2 Noise IK sessions, full-mesh opus datagrams over Bonjour UDP.
- Local mix of N-1 streams on each device.
- Leave (`mesh_gc_leave`); auto-end when only one peer remains.
- UI: reuse `group_call_lobby_screen` and `group_call_active_screen` from Phase 1 LiveKit, rewired to a new mesh BLoC. Old LiveKit `GroupCallBloc` becomes dead code behind the existing `AppConfig.isDev` FAB until removed.

**Out of scope (separate phases / backlog):**

- Late-join after Active starts.
- Wi-Fi Direct / Multipeer / hotspot ("device-created network" phase).
- LiveKit fallback for peers not on the same Wi-Fi.
- Mute-other, kick, host role / privileges.
- Video.
- Call recording.

**Dependency:** 1-on-1 mesh voice baseline is stable. Any regression in UDP datagram delivery is fixed at the `BonjourTransport` / `MultiTransport` layer and benefits both 1-on-1 and group; it does not block the group work above the transport.

## Architecture

```
        ┌──────────────────────────────┐
        │   GroupMeshCallBloc          │   UI state machine
        │   states: Idle → Inviting    │
        │           → Lobby → Active   │
        │           → Ended            │
        └──┬───────────────────────┬───┘
           │ command/event         │ render
           ▼                       ▼
   ┌──────────────────┐    group_call_lobby_screen
   │ GroupMeshCall    │    group_call_active_screen
   │ Service          │    (grid of N tiles)
   │ ─ room state     │
   │ ─ per-peer FSM   │
   │ ─ N audio paths  │
   └──┬───────────┬───┘
      │           │
      ▼           ▼
  signaling   audio
  (envelopes) (datagrams)
      │           │
      ▼           ▼
 ┌────────────────────────────┐
 │ MeshMessagingService       │   envelopes: mesh_gc_invite/accept/decline/leave/end
 │ (Phase 2, existing)        │
 └────────────────────────────┘
 ┌────────────────────────────┐
 │ MultiTransport             │   per-peer Noise IK session +
 │  └─ BonjourTransport (UDP) │   AEAD frames (header + ciphertext)
 └────────────────────────────┘
 ┌────────────────────────────┐
 │ GroupMeshAudioEngine       │   mic → 1× opus encoder → fanout(N-1)
 │  capture: 1                │   per peer: opus decoder + jitter buffer
 │  decoders: N-1             │   N-1 PCM streams → mixer (int16 sum, clip) → playback
 │  mixer: 1                  │
 │  playback: 1               │
 └────────────────────────────┘
```

Key departures from 1-on-1:

1. **One service manages one call, with N (peer, session, decoder, jitterBuf) tuples** keyed by peerId. `MeshVoiceService` (existing) is unchanged and continues to serve 1-on-1.
2. **Audio engine refactors:** one capture and one encoder (opus output is recipient-agnostic), but **N-1 decoders, N-1 jitter buffers, and a mixer**. This is the largest implementation change.
3. **Wire format unchanged:** frame `[1 type | 4 callId | 8 seq | ciphertext]`. `callId` is reinterpreted as `roomId` for group calls; sender identity is implicit from the transport's source-peer mapping. All participants share one 32-bit `roomId` generated by the host. Each per-peer Noise session has its own monotonically increasing `seq`.
4. **Signaling envelopes** are new types (see below).
5. **Handshake fanout** runs in parallel from each accepted peer to every other accepted peer. Concurrent-handshake races resolved by lexicographic devicePk ordering: the peer with the numerically smaller devicePk byte-string initiates; the other waits for message 1.

## Signaling envelopes

All envelopes flow through the existing `MeshMessagingService` (Phase 2). They are JSON payloads inside Noise-encrypted envelopes.

| Type | From → To | Payload | When |
|------|-----------|---------|------|
| `mesh_gc_invite` | host → each invitee | `{roomId, hostDevicePk, participants:[devicePk], startedAt}` | Host taps Start |
| `mesh_gc_accept` | invitee → host + every other participant | `{roomId, devicePk}` | Invitee taps Accept |
| `mesh_gc_decline` | invitee → host only | `{roomId, devicePk, reason?}` | Invitee taps Decline or 30 s timeout fires |
| `mesh_gc_leave` | peer → every remaining peer | `{roomId, devicePk}` | Peer taps Hang up; also when the local roster reaches 0 the call ends locally without an envelope |
| `mesh_gc_keepalive` | peer → each per-session peer | `{roomId, seq}` | 1 Hz; fallback path so the per-peer 3 s watchdog does not fire when UDP datagrams are momentarily silent (e.g., mid-mute) |

## State machine — host

```
Idle ─[user starts call, picks N contacts]─> Inviting

Inviting:
  fanout mesh_gc_invite to each invitee via Phase 2 messaging
  enter Lobby (UI: lobby with N tiles "calling…")
  start 30 s timeout

Lobby:
  on mesh_gc_accept from peer X:
    X tile → "joined"
    if all invitees accepted OR (timeout fired AND ≥1 accepted):
      → Active
  on mesh_gc_decline from peer X:
    X tile → "declined", remove from room
    if no remaining invitees → Ended (no peers joined)
  on 30 s timeout:
    if ≥1 accepted → Active (without non-responders)
    else → Ended (no answer)

Active:
  ensure Noise IK session to each accepted peer
    (initiate iff our devicePk is lexicographically smaller)
  start audio engine: mic → opus encoder → fanout to each established session
  per-peer datagram watchdog (3 s) and keepalive ticker (1 Hz)
  on peer drop (watchdog OR mesh_gc_leave):
    remove tile, tear down that session
    if 0 peers remain → Ended
  on user Hang up:
    send mesh_gc_leave to each peer → Ended
```

## State machine — invitee

```
Idle ─[receives mesh_gc_invite]─> Ringing

Ringing:
  show native incoming UI (CallKit on iOS, full-screen notification on Android)
  start 30 s self-timeout
  on user Accept:
    send mesh_gc_accept to host + every other participant in the invite list
    enter Lobby (UI: "joining…" + roster from invite list)
  on user Decline OR 30 s expire:
    send mesh_gc_decline to host → Idle

Lobby / Active / Ended: same as host
```

## Edge cases

1. **Concurrent handshake:** Peers A and B both see each other's accept and both try to initiate Noise IK. The peer with the numerically smaller devicePk byte-string is the sole initiator; the other waits for message 1. Stateless and deterministic.
2. **Late accept (peer accepted after Active started):** Out of scope in v1. Host ignores the accept and sends `mesh_gc_end{reason:lateAccept}` to that peer. Late-join is a future phase.
3. **Host equality:** v1 treats the host as a regular peer with no special privileges. Host leaving sends `mesh_gc_leave`; the room continues while ≥2 peers remain.
4. **Network partition:** A loses B but still sees C. Both A↔B watchdogs fail and the pair drops each other. A↔C continues. Rosters can briefly diverge between A's and C's views — acceptable; each peer maintains its own roster locally.
5. **Handshake failure (Noise IK fails or 10 s timeout):** That peer is marked "connection failed" in the UI, excluded from the audio fanout; the rest of the room runs normally.
6. **Hard cap of 5 peers (including host):** contact picker prevents selecting more than 4 invitees; invites exceeding the cap are rejected client-side.

## Audio engine

```
mic → PCM(20 ms @ 16 kHz) → opus encode ──┬── peer A session → datagram
                                          ├── peer B session → datagram
                                          └── peer C session → datagram

peer A datagram → opus decoder A → jitter buf A → PCM_A ┐
peer B datagram → opus decoder B → jitter buf B → PCM_B ├→ Mixer → playback
peer C datagram → opus decoder C → jitter buf C → PCM_C ┘
                                                          (int16 sum, hard clip)
```

Decisions:

- **One encoder.** Opus output is independent of the receiver; it is re-encrypted per session via different Noise k1 keys, but encoded bytes are identical. Encoding once saves CPU vs N-1×.
- **N-1 decoders + N-1 jitter buffers**, independent. Each peer has its own rate drift, latency, and PLC state; they cannot share buffer state.
- **Mixer** runs on the capture period (20 ms / 50 Hz). For each tick: read the latest 320-sample int16 frame from each peer's jitter buffer (zero-fill if empty), sum element-wise, hard-clip to int16 range, write to playback. Hard clip is acceptable for voice at N≤5; a normalizer with auto-gain is backlog.
- **Tick synchronization:** master tick is the capture period. Missing peer data → silence frame, never block.
- **Files:** new `lib/core/audio/group_mesh_voice_audio_engine.dart` next to the existing `mesh_voice_audio_engine.dart`. Not a subclass — separate class. The 1-on-1 engine stays untouched. Shared helpers (FFI bindings, native capture/playback, jitter-buffer logic) are factored into a common module only if duplication becomes painful; otherwise duplicate is fine for v1.
- **Mic conflict:** mic is a single resource. While a 1-on-1 call is active, the group FAB is disabled with a "busy" modal. While a group call is active, incoming 1-on-1 invites auto-decline with reason "busy".
- **Memory footprint at N=5:** ~4× decoder state (~30 KB each) + 4× jitter buffer (~120 KB at 60 ms depth) ≈ 600 KB. Acceptable for phones.
- **CPU estimate:** mid-tier Android (Pixel 4 class), opus encode 1× + decode 4× ≈ 6% sustained. iOS faster. No thermal concerns expected.

Reused unchanged:

- `MeshDatagramCipher` (per-peer Noise k1/k2 + ChaCha20-Poly1305 + replay window).
- `MeshVoiceFrame` (header layout, framing).
- `BonjourTransport.sendDatagram()` / inbound emit path.
- `MultiTransport` peer-learning (Phase 1k synthetic discovery from inbound).
- Noise IK handshake machinery.

## UI

**FAB "Group mesh call"** in `call_history_screen.dart` replaces the current `AppConfig.isDev`-gated LiveKit FAB. Visible on PROD after v1 ships. Old LiveKit FAB is removed in the same change.

**`new_group_call_screen.dart`** (existing) — contact picker:

- Shows only contacts whose ≥1 device is currently mesh-reachable (visible via `MeshPeerEligibilityWatcher`).
- Off-mesh contacts are greyed out, disabled, with a "not on this Wi-Fi" badge.
- Hard cap of 4 invitees (5 including host).
- "Start" button calls `GroupMeshCallBloc.start(roomId, participants)`.

**`group_call_lobby_screen.dart`** (existing) — lobby:

- N tiles each showing avatar, name, status (`calling…` / `joined` / `declined` / `no answer`).
- Host's tile shows status "host"; others are invitees.
- Invitee sees their status "joining" plus the rest of the invite roster.
- Cancel / Decline button.

**`group_call_active_screen.dart`** (existing) — active call:

- Grid of N tiles (one self, others peers).
- Per-tile: avatar, name, mic-on/off, speaking indicator (RMS over recent decoded frames > threshold), connection status (green / yellow / red).
- Bottom bar: Mute self, Speaker on/off, Hang up.
- Top bar: "Mesh • N participants • duration".

**Incoming ring / native UI** — invitee side:

- iOS: CallKit via `flutter_callkit_incoming`, same path as 1-on-1 mesh voice.
- Android: foreground service + full-screen notification (Phase 3d.3 mechanism for background mesh calls).
- Title: "Group call from <host>".
- Subtitle: "Plus <N-1>: Alice, Bob, …".

**BLoC structure:**

- `GroupMeshCallBloc` (new) next to existing LiveKit `GroupCallBloc`. Independent state hierarchy: `Idle`, `Inviting`, `Lobby({roster})`, `Active({roster, durationSec})`, `Ended({reason})`, `Error({message})`.
- Events: `Start(participants)`, `AcceptInvite(roomId)`, `Decline(roomId)`, `Leave()`, `ToggleMute()`, plus peer-event stream subscribers.
- Old `GroupCallBloc` (LiveKit) becomes dead code, removed in a follow-up cleanup after the mesh path stabilizes on PROD.

**Navigation:**

- Existing GoRouter route `/group-call/:roomId` is rewired to the mesh BLoC.
- Deep-link parameter `?transport=mesh` for future-proofing if a LiveKit variant ever returns.

**Coexistence with 1-on-1:**

- 1-on-1 active → group FAB disabled with a "busy" modal.
- Group active → incoming 1-on-1 invite auto-declined with reason "busy".

## Testing strategy

**Unit tests (`test/`):**

1. `group_mesh_call_bloc_test.dart` — state machine: Idle → Inviting → Lobby → Active → Ended across scenarios (all accept, partial decline, timeout, host leaves, last peer leaves). Mocked `GroupMeshCallService`. ~12 cases.
2. `group_mesh_audio_mixer_test.dart` — mixer: single peer passthrough; N peers of identical tones produce summed amplitude with clip; empty jitter buf is zero-filled (no crash); int16 clip behavior at max+max.
3. `group_mesh_call_service_test.dart` — orchestration: handshake fanout with deterministic role assignment by lexicographic devicePk; peer drop (watchdog) shrinks roster without killing remaining sessions; concurrent accept races.
4. `mesh_gc_envelope_test.dart` — JSON serialization of invite / accept / decline / leave / end / keepalive envelopes.

**Integration tests (`integration_test/`):**

5. `group_mesh_call_test.dart` — two emulators (5554 host, 5556 invitee, N=2 minimum). Login both; host creates the group call with one invitee; invitee receives native UI (mocked `flutter_callkit_incoming` on the emulator); Accept transitions both to Active; verify roster on both sides. Then immediately start a second group call to the same invitee — verifies regression coverage for the Phase 1 LiveKit Defect #8 (sequential calls) does not recur in the mesh path. Audio path is not asserted (emulators lack realistic mic), but session establishment is.

**Hardware smoke (manual, documented in the implementation plan):**

- 3 devices (1 iPhone + 2 Android) on the same Wi-Fi.
- Host starts a group call; both invitees see full-screen incoming.
- All accept; audio is audible in both directions on all 3 devices.
- One hangs up; the other two continue.
- Sanity: no audible echo or noticeable dropouts over 2-3 minutes.

**Backend smoke (`taler_id_tests`):** none. The feature is entirely client-side; the backend is not involved.

**Test accounts:** `integration_test@taler-test.com`, `integration_test_2@taler-test.com` exist on DEV and PROD. For 3-peer tests, add `integration_test_3@taler-test.com` on both environments (a one-time runbook step before the integration test lands).

**Explicitly NOT covered by automated tests in v1:**

- Reconnect after a temporary network drop.
- Recovery from mid-call Wi-Fi switch.
- Late-join.

**Manual QA checklist (lives alongside the implementation plan):**

- N=2, 3, 4, 5.
- iOS-iOS, Android-Android, iOS-Android mixed.
- Wi-Fi with client isolation: expected behavior is "discovery sees, audio does not flow → call shows 'could not establish connection'".
- Wi-Fi switch mid-call: expected is "call ends cleanly, no hang".

## Risks and mitigations

- **Mic conflict with 1-on-1** is grossly handled (FAB disabled / auto-decline). If users find this annoying we revisit, but the constraint is honest: one mic, one call.
- **Bonjour discovery flakes** on iOS — `MeshDiscoverySupervisor` already mitigates this for 1-on-1; the group path inherits the same supervision since it uses the same transport.
- **Mixer hard-clip artifacts** at N=5 with multiple loud speakers — acceptable for voice; if it becomes a complaint, soft-clip / auto-gain is a backlog item.
- **Sequential-call defect (Phase 1 LiveKit Defect #8) regression** in the mesh path — explicitly covered by integration test #5.
- **Late-join requests post-ship** — design accommodates by structuring the roster as a per-peer view, not a global truth; adding `mesh_gc_member_added` and current-roster delivery is a future increment without rework.
